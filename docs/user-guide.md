# Юзер-гайд Vector Prediction: кто что делает

Полный цикл прогноза: от выгрузки данных до плана производства.
Роли разделены: люди готовят данные и принимают решения, агенты считают и проверяют.

---

## Роли

| Кто | Что делает |
|-----|------------|
| **Специалист по продажам** | Выгружает историю продаж из 1С/CRM в CSV; знает план акций и цен |
| **Маркетолог** | Составляет план промо/рекламы на прогнозный период |
| **Директор / планировщик** | Ставит задачу (что прогнозировать, на какой срок), принимает решение по результату |
| **Агент-сборщик данных** | Проверяет файлы по чек-листу, чинит типовые ошибки оформления, формирует history.csv + plan.csv |
| **Агент-прогнозист** | Запускает контур A (2.5), готовит отчёт с интервалами и метриками |
| **Агент-исследователь** | Запускает контур B (3.0) для сравнения моделей — только внутренний отчёт |
| **Агент-ревьюер** | Проверяет соответствие лицензии и качество прогноза перед передачей людям |

---

## Путь данных по шагам

### Шаг 1. Специалист по продажам — выгрузка истории

Откуда: 1С / CRM / Excel-журнал.

Что выгрузить (минимум):
- дата по дням,
- продажи по каждому продукту (кг или штуки — что-то одно),
- факты акций по дням (1 = была акция, 0 = нет).

Что докинуть, если есть (повышает точность):
- посещаемость/трафик,
- цены по дням,
- отметки праздников.

Период: минимум 4 месяца, лучше 1–2 года. Шаг — день.

Выдаёт: файл-сырец (как получится — Excel, выгрузка 1С, что угодно).

### Шаг 2. Маркетолог — план на прогнозный период

Составляет таблицу плана на будущие дни (горизонт обычно 14 дней):

```
date,promo,holiday,price_sosiski
2026-09-05,1,0,319.90
2026-09-06,1,0,319.90
```

Правило: сюда попадает только то, что известно ЗАРАНЕЕ (акции, праздники, цены
по будущему прайсу). Погода — только если есть реальный прогноз погоды.
Выдумывать будущие числа нельзя.

Выдаёт: plan.csv на N дней вперёд.

### Шаг 3. Агент-сборщик — проверка и склейка

Автоматически:
1. Проверяет чек-лист (docs/data-guide.md): единицы, формат чисел, «итого»-строки,
   пропуски дат, смешение шт/кг.
2. Типовые ошибки чинит сам и показывает дифф («было → стало»); спорное —
   возвращает специалисту вопросом, не молча.
3. Склеивает history.csv (прошлое) + plan.csv (будущее) в формат для пайплайна.
4. Гонит preflight `scripts/check_system.py` — RAM/диск/веса на месте.

Выдаёт: готовые CSV + короткий отчёт «что поправил, что спросил».

### Шаг 4. Агент-прогнозист — контур A (прод)

```bash
python scripts/campaign_forecast.py --input data/ready/history.csv \
    --date-col date --value-cols sosiski_kg,vetchina_kg \
    --covariate-col promo --holdout 14 --horizon 14 --outdir out/
```

Что делает:
- точечный прогноз + 60/80% интервалы по каждому продукту,
- аномалии в истории (OK / WARNING / CRITICAL по квантилям),
- метрики точности на holdout (MAE/RMSE/MAPE) — честная оценка качества,
- PNG-график и CSV для людей.

Выдаёт: out/*.csv + *.png + metrics.json.

### Шаг 5. Агент-ревьюер — контроль качества

Проверяет перед передачей людям:
- [ ] метрики на holdout адекватны (MAPE в ожидаемом коридоре 5–15% для продаж);
- [ ] покрытие 80% интервала близко к 80% (если сильно ниже — данные плохие);
- [ ] ковариат-план реально попал в прогноз (промо-дни подняты);
- [ ] аномалии истории объяснимы (вопрос специалисту, если нет);
- [ ] лицензионный чек: в отчёте только контур A (см. docs/license-compliance.md).

Если что-то не сходится — возвращает прогнозисту с конкретным замечанием,
а не передаёт сырые цифры людям.

### Шаг 6. Директор / планировщик — решение

Получает: таблицу «день → forecast / cautious / optimistic» + график + метрики.

Как читать:
- **forecast** — план производства/закупки по умолчанию;
- **cautious** (10-й перцентиль) — нижняя граница; для скоропорта (охлаждёнка)
  держаться ближе к ней;
- **optimistic** (90-й перцентиль) — верхняя граница; запас на заморозку/долгий срок.

Решение принимает человек. Прогноз — инструмент, не приказ.

### Параллельно: агент-исследователь — контур B (3.0)

Не участвует в производственном цикле. Запускается по отдельной задаче
«сравнить модели»:

```bash
python scripts/research_bench.py --input data/ready/history.csv \
    --date-col date --value-col sosiski_kg --covariate-col promo --holdout 14
```

Результат: JSON со сравнением MAE/скорости 2.5 vs 3.0 — для внутреннего отчёта
«какую модель использовать». Прогнозы 3.0 в планы производства не попадают
(лицензия: docs/license-compliance.md).

## Схема потока

```
ПРОДАЖИ ──сырец──┐
                 ├─► АГЕНТ-СБОРЩИК ──history.csv + plan.csv──┐
МАРКЕТОЛОГ ─план─┘                                          │
                                                            ▼
                                              АГЕНТ-ПРОГНОЗИСТ (контур A, 2.5)
                                                            │
                                          АГЕНТ-РЕВЬЮЕР (качество + лицензия)
                                                            │
                                                            ▼
                                       ДИРЕКТОР/ПЛАНЕР (решение по плану)
                                                            ▲
АГЕНТ-ИССЛЕДОВАТЕЛЬ (контур B, 3.0) ── внутр. отчёт о моделях ┘ (не в прод)
```

## Каденция

| Цикл | Периодичность | Кто |
|------|--------------|-----|
| Обновление истории | раз в неделю (выгрузка за прошедшую неделю) | продажи → агент-сборщик |
| Прогноз на 2 недели | еженедельно по обновлённой истории | агент-прогнозист |
| Сравнение 2.5 vs 3.0 | раз в месяц или после заметного сдвига качества | агент-исследователь |
| Проверка лицензии 3.0 | раз в месяц (перевели ли в Apache / BigQuery) | агент-исследователь |

## Типовые вопросы

**Кто отвечает за качество данных?** Специалист по продажам отвечает за полноту
и правдивость выгрузки; агент-сборщик — за формат и типовые ошибки.

**Кто отвечает за прогноз?** Агент-прогнозист отвечает за корректный запуск и
метрики; решение по плану — человек.

**Можно ли взять прогноз 3.0 вместо 2.5?** Нет (лицензия). 3.0 — только
сравнение моделей внутри. Когда Google переведёт веса в Apache или включит
3.0 в BigQuery — пересмотрим (проверка раз в месяц, см. выше).

**Что если метрики плохие (MAPE > 15%)?** Значит, данных мало или ряд слишком
шумный: увеличить историю, добавить ковариаты (акции, праздники), агрегировать
продукты в группы. Прогноз всё равно выдаётся, но с пометкой о низкой надёжности.

**Прогноз ≠ истина.** Модель не знает о внезапных событиях (срыв поставки,
новый конкурент, резкая новость). План по прогнозу — база; корректировки
руководителя поверх — нормальная практика.
